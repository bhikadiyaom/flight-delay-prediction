# Deployment guide

Target: **Vercel** (client) + **Render** (API and ML service) + **MongoDB Atlas** (database). All have free tiers.
You need accounts and, optionally, an AviationStack key; nothing here can be done without your own credentials.

```
Vercel (React)  ->  Render: fdp-server (Node)  ->  Render: fdp-ml-service (FastAPI)
                          \-> MongoDB Atlas          \-> committed model artifacts (+ optional analytics parquet)
```

Deploy in this order (each step needs the URL or secret from the previous one):
**Atlas -> ML service -> API -> client -> CORS update -> GitHub secrets**.

## 1. MongoDB Atlas

1. Create a free cluster (M0). Database Access: create a user with a strong password.
2. Network Access: allow `0.0.0.0/0` (Render free instances have no fixed IP) **and rely on the strong password**, or use Atlas private networking on a paid plan.
3. Connect > Drivers > copy the `mongodb+srv://...` string, add the database name: `.../flight-delay?retryWrites=true&w=majority`.
4. **URL-encode special characters in the password** (`@` -> `%40`, `#` -> `%23`).

Collections and indexes are created automatically on first start.

## 2. ML service (Render web service, Docker)

Use the blueprint `server/render.yaml` (Render > New > Blueprint; point it at that file, or copy it to the repo root) or create manually:

| Setting | Value |
|---|---|
| Runtime | Docker, Dockerfile path `./ml-service/Dockerfile`, **Docker context `.` (repo root)** |
| Plan | Free (512 MB) |
| `INTERNAL_API_KEY` | generated by Render, **copy it for step 3** |
| `DUCKDB_MEMORY_LIMIT` | `300MB` (a 512 MB host needs this) |
| Health check | leave **empty** (`/health` requires the secret header, which Render's checker cannot send) |

The trained models are inside the image (committed artifacts, about 4 MB), so predictions work immediately.

### Analytics data (optional but needed for Insights / History / Risk map)

The 145 MB parquet is not in git. Package it once on a machine that has it:

```powershell
python scripts/pack-data.py        # writes dist-data/flights-parquet.tar.gz and prints PARQUET_SHA256
```

Upload that file as a **GitHub Release asset** (or any HTTPS host), then set on the ML service:

```
PARQUET_URL=https://github.com/<you>/<repo>/releases/download/data-v1/flights-parquet.tar.gz
PARQUET_SHA256=<printed checksum>
```

On boot the container downloads it once, **verifies the checksum**, and unpacks it. A failed or tampered download is ignored (the service
still starts; analytics just answers 503). Note: Render free instances have ephemeral disks, so the download repeats after every restart; for a
persistent copy attach a disk or use a paid plan.

## 3. API server (Render web service, Docker)

| Setting | Value |
|---|---|
| Dockerfile / context | `./server/Dockerfile`, context `./server` |
| Health check path | `/api/v1/health` (200 unless the DB is down) |
| `NODE_ENV` | `production` (turns on `trust proxy` for correct client IPs) |
| `MONGODB_URI` | step 1 |
| `JWT_SECRET` | 32+ random characters (Render can generate) |
| `ML_INTERNAL_KEY` | **exactly** the ML service's `INTERNAL_API_KEY` |
| `ML_SERVICE_URL` | `https://fdp-ml-service.onrender.com` (the exact URL Render shows) |
| `CLIENT_URL` | filled in step 5 |
| `AVIATIONSTACK_KEY`, `ADMIN_EMAILS`, `SMTP_*` | optional |

Check `https://<api>/api/v1/health`: expect `{"status":"ok","db":{"connected":true},"ml":{"reachable":true,...}}`. `degraded` means the ML service is unreachable or the keys differ.

## 4. Client (Vercel)

1. Import the repo, set **Root Directory** to `client`. Framework preset: Vite (build `npm run build`, output `dist`).
2. Environment variable: `VITE_API_URL=https://<your-api>.onrender.com` (**build time**; redeploy after changing it).
3. `client/vercel.json` already provides the SPA rewrite (refresh on `/eda` must not 404) and the security headers.
4. **CSP**: `connect-src` in `client/vercel.json` allows `https://*.onrender.com`. With a custom API domain, replace it with your exact API origin.
   If you ever edit the inline theme script in `client/index.html`, update its `sha256-...` hash in `vercel.json` and `nginx.conf` (the client test prints the expected value).

## 5. Connect them (CORS)

Set the API's `CLIENT_URL` to the exact Vercel origin, e.g. `https://flight-delay.vercel.app` (**no trailing slash**; comma-separate several, e.g. a preview and a custom domain) and redeploy the API.

## 6. GitHub Actions secrets (optional auto-deploy)

`.github/workflows/deploy.yml` runs after CI passes on `main` and **skips any step whose secret is missing**:

| Secret | Where to get it |
|---|---|
| `RENDER_ML_DEPLOY_HOOK`, `RENDER_SERVER_DEPLOY_HOOK` | Render service > Settings > Deploy Hook |
| `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` | Vercel account token; `.vercel/project.json` after `vercel link` |

You can instead use Render's and Vercel's own Git auto-deploys and ignore this workflow.

## 7. Verify (5 minutes)

1. `GET <api>/api/v1/health` -> `ok`.
2. Open the site, **Predict**: pick DL, ATL to JFK, submit. You should see gauges and "Why this score?".
3. **Live flight**: try `DL400`. Without an AviationStack key you get the "Demo data" badge, which is correct.
4. Register with an email listed in `ADMIN_EMAILS`, open **Admin > Usage**, then **Models > Refresh from ML service**.
5. **Insights** loads only if the analytics data was set up in step 2.

## 8. Operating notes

- **Free tier cold starts:** both Render services sleep after inactivity; the first request can take 30-60 s (the ML service loads models on boot). The client shows loading states and a retry button.
- **Quota:** AviationStack free tier is about 100 calls/month. The server stops at 90% and serves cache/demo data. Watch it in **Admin > Usage**.
- **Cost control:** rate limits (30 anonymous / 120 logged-in predictions per 15 min) protect the free tiers; tune `RATE_LIMIT_*`.
- **Retraining a new model:** commit the new `ml-service/artifacts`, redeploy the ML service, then **Admin > Models > Refresh** (this also clears the cached comparison).
- **Rotating secrets:** new `JWT_SECRET` logs everyone out; a new ML key must be changed on both Render services.
- **Logs:** Render dashboard (structured JSON from the API; request ids in `X-Request-Id`).

## 9. Security checklist before sharing the link

- [ ] `JWT_SECRET` and `ML_INTERNAL_KEY` are random and **not** the example values
- [ ] No `.env` committed (`git ls-files | findstr /i "\.env$"` prints nothing)
- [ ] `CLIENT_URL` is the exact production origin (not `*`)
- [ ] Atlas user password is strong; Atlas IP rule is reviewed
- [ ] `ADMIN_EMAILS` lists only your addresses
- [ ] The ML service URL is not advertised anywhere (it is protected by the key, but needs no audience)

## 10. What was not verified here

The dev machine had no Docker, so the three images were validated by (a) YAML and cross-reference checks, (b) running the ML service and API
from copies containing only the files each Dockerfile copies (production-only npm dependencies for the API), and (c) testing the entrypoint's
download logic. CI builds all three images on every push; the first `docker compose up --build` on a Docker machine is the final proof.
Render/Vercel/Atlas were never touched (no credentials), so steps 1-6 above are the documented procedure, not a recording.
